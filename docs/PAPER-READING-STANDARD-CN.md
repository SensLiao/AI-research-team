# 论文深读与证据型 Markdown 标准（可读性优先版）

> 核心优先级：**可读性 > 证据完整性 > 方法深度 > 批判性 > 全面性 > 项目迁移 > 机器治理**。
>
> 本标准面向需要支撑研究决策、实验设计、论文写作和复现工作的深度阅读。它不是摘要复述模板，也不是把若干内部字段填满的验收表。
>
> 语义产品版本：`paper-reading/v3`。图片是可选载体，不是交付真相本身：能稳定保存时优先嵌入；不能保存时，必须提供来源、图中内容、关键数字、支持范围与不支持范围的完整文字等价物。

---

## 1. 什么才算“深读完成”

一份合格的深读，应当让一个没有参与阅读过程、但具备相关背景的研究者，在只看 Markdown 的情况下完成下列任务：

1. 用自己的话说清论文解决了什么问题、为什么值得解决、作者到底提出了什么。
2. 区分作者的主张、论文直接给出的证据、读者的解释，以及迁移到当前项目后的推断。
3. 重建数据、方法、训练、推理、评价和统计流程，而不是只抄架构名或公式编号。
4. 对支撑核心结论的原始图、表或公式完成真实检查，并理解其中的坐标、单位、比较条件和关键数字；截图能稳定保存时嵌入，否则提供完整文字等价物。
5. 判断实验是否公平，主要结论是否被证据充分支持，有没有泄漏、选择性报告、外推或统计问题。
6. 知道论文在哪些条件下成立、在哪些条件下不成立，以及最强替代解释是什么。
7. 判断论文能否复现、最小复现路径是什么、缺失材料会阻断哪一步。
8. 在充分理解论文本身后，再判断它与当前项目的直接关系、迁移前提和下一步动作。

以下情况**不算深读**：

- 只复述摘要、引言和结论。
- 列出一堆 `Claim ID`、`Contribution ID`、图号、表号，却没有可读的结论句和证据解释。
- 只写“Figure 3 支持主张”，既不提供图片，也不摘录关键数字、不解释它支持到什么程度。
- 大部分内容都围绕当前项目，论文自己的研究问题、方法边界和证据反而很少。
- 把“代码存在”“作者说做了外部验证”直接等同于可复现或可信。
- 用字段数量、worker 数量、状态码或版本号代替科学判断。

## 2. 交付物结构：人类文档优先，机器信息退到侧边

推荐目录：

```text
papers/<paper-key>/
├── <paper-key>.md                 # 人类主阅读文档
├── source/
│   ├── paper.pdf                  # 使用的论文版本
│   └── supplement.pdf             # 如有
├── assets/                         # 可选；仅在图片能稳定保存时创建
│   ├── fig-01-problem-setting.png
│   ├── fig-02-method-overview.png
│   ├── table-01-main-results.png
│   ├── fig-05-failure-cases.png
│   └── reconstructed-pipeline.svg
└── evidence.json                  # 可选；机器证据层，不进入主阅读流
```

### 2.1 主 Markdown 只保留人真正需要看的内容

主文档中可以出现论文标题、作者、年份、来源、页码、图号和 DOI，但以下信息默认不放在正文显眼位置：

- 内部 contribution/claim/idea 编号；
- bundle、worker、wave、owner；
- schema、contract version、hash、receipt；
- 自动评分的中间字段；
- 流程编排和版本治理细节。

这些信息如确实需要保留，可进入 YAML front matter、HTML 注释或独立 JSON：

```markdown
<!-- machine_key: main-result-low-label -->
```

它不会在正常 Markdown 渲染中打断阅读。

### 2.2 图片并不是“写进二进制 Markdown”

Markdown 通常保存的是图片路径或 URL，图片文件放在 `assets/` 目录。主文档通过相对路径展示图片，这样仓库复制、离线阅读和版本迁移都更稳定。

## 3. 阅读等级与最低交付强度

| 等级 | 适用场景 | 最低交付 |
|---|---|---|
| 快速收录 | 判断是否值得继续读 | 一句话结论、问题与贡献、三条核心发现、一张最关键图或表、最大局限、是否升级深读 |
| A-core 深读 | 核心方法、基线、实验设计或论文写作依据 | 完整论文内在分析、3–7 个关键结论证据包、3–8 个关键视觉证据说明（图片可选、文字等价物必需）、方法重建、数据与数值审计、批判性评价、复现路径、项目迁移 |
| A+ 基石论文 | 将成为方法依据、论文主线或复现实验对象 | A-core 全部内容，加补充材料审计、邻近工作差异矩阵、引用核验、复现尝试或可执行复现计划、失败模式和外部有效性扩展 |

图片数量不是硬性凑数。若论文只有一张真正承载结论的图，应解释为何；若有大量重要图表，则不能只选最有利的几张。

## 4. 文档顺序：先把论文本身讲明白，再谈项目

推荐篇幅占比：

- **70%–80%：论文内在理解与证据审计**；
- **10%–20%：相关工作与领域位置**；
- **10%–15%：当前项目迁移与下一步**。

项目关系必须放在论文内在分析之后。原因很简单：读者需要先知道论文真实做了什么，才能判断它对项目意味着什么。项目关联不能替代论文理解。

推荐顺序：

1. 一屏决策摘要；
2. 问题、背景与贡献；
3. 数据与研究设计；
4. 方法重建；
5. 关键结论—证据包；
6. 数值、图表、消融、稳健性与失败审计；
7. 批判性评价；
8. 可复现性；
9. 文献位置；
10. 项目迁移；
11. 下一步。

## 5. 可读性规则：内部编号不能成为内容本身

### 5.1 禁止把不透明 ID 放在标题或首列

不推荐：

```markdown
### C-017
| Claim ID | Evidence ID | Contribution ID |
```

推荐：

```markdown
### 关键结论一｜低标注条件下，方法提升主要来自边界一致性约束
```

如机器层必须有稳定键：

```markdown
<!-- claim_key: low-label-boundary-consistency -->
```

### 5.2 每个“贡献”必须写成可判断的完整句

不要写：

- Contribution 1：新模块；
- Contribution 2：新数据；
- Contribution ID：7。

应写：

- **方法贡献：**在不增加测试时交互的前提下，引入跨尺度边界一致性损失，用于缓解小病灶漏检。
- **实证贡献：**在两个外部中心上检验域偏移，并报告按病灶大小分层的性能变化。
- **机制贡献：**通过消融显示性能提升主要来自标签稀疏时的边界约束，而不是参数量增加。

### 5.3 中英文术语规则

- 首次出现时写“中文解释（英文全称，缩写）”。
- 后文只保留必要缩写。
- 不把 `load-bearing`、`oracle quarantine`、`reconciliation` 等内部术语直接丢给普通读者；应翻译并解释。
- 表格列名优先使用中文；英文原词可放括号。
- 数字只在有科学含义时出现，不能让编号成为视觉主体。

### 5.4 长表之前必须先有叙事结论

任何超过五行的证据表、结果表或相关工作表之前，都先写 2–5 句结论，告诉读者：

- 这张表回答什么问题；
- 最关键的数字或差异是什么；
- 阅读时应注意什么限制。

## 6. 证据类型必须明确标注

建议使用以下四类标签，而不是模糊地把所有内容写成同一种语气：

- **[作者主张]**：作者在正文、摘要或结论中明确声称。
- **[直接证据]**：可由实验、图表、公式、证明或原始材料直接支持。
- **[评审判断]**：阅读者基于证据作出的解释、质疑或可信度判断。
- **[项目迁移]**：将论文发现映射到当前项目后的推断，必须写明额外假设。

示例：

```markdown
[作者主张] 该方法在低标注场景中显著优于监督基线。

[直接证据] Table 2 中 10% 标注设置下 Dice 提高 3.2 个百分点；但只报告三次运行的均值，没有置信区间。

[评审判断] 结果支持“在该数据与训练预算下有效”，不足以支持“普遍适用于低资源医学分割”。

[项目迁移] 若当前项目的主要瓶颈同样来自边界标签稀疏，该损失值得先做小规模验证；前提是我们的预处理和病灶尺度分布相近。
```

## 7. 图片、截图和图表证据标准

### 7.1 必须检查并解释哪些视觉材料

A-core 深读至少应真实检查并解释论文中承载主要结论的视觉证据。图片文件能稳定保存时优先嵌入；不能保存时不得阻塞 Markdown，但必须写完整文字等价物。适用对象包括：

- 问题设定或整体框架图；
- 方法流程或架构图；
- 主结果表；
- 关键消融或敏感性分析；
- 外部测试、分层结果或泛化结果；
- 典型成功与失败案例；
- 关键公式、定理或证明结构；
- 数据流、样本筛选或队列流程图。

### 7.2 图片可保存时的截图要求

1. 从实际使用的 PDF/supplement 版本截取，记录页码与图表编号。
2. 优先裁出图表及其标题/必要注释，不要只放整页缩略图。
3. 不得裁掉坐标轴、图例、单位、误差条、样本量、显著性标记和关键脚注。
4. 分辨率必须足以在 Markdown 页面直接阅读；看不清的图等同于没有放图。
5. 原论文图与 agent 重绘图必须明确区分：
   - `原论文图`：忠实截图；
   - `阅读者重建图`：用于解释方法，不能伪装成作者原图。
6. 每张图下方必须有“来源、读图结论、关键数字、支持边界”。
7. 图表不能只负责装饰；若正文不引用和解释，应删除。

### 7.3 无法嵌图时的文字等价物

无法稳定保存图片、许可不适合复制、或当前交付只保留 Markdown 时，使用以下结构替代图片：

```markdown
> **视觉证据（未嵌图）｜原论文第 8 页，Fig. 3**
> - 图中内容：横轴、纵轴、分组、单位和比较对象。
> - 关键观察：最重要的趋势、异常与数字。
> - 支持：该图允许得出的最强结论。
> - 不支持：因果、泛化、机制或临床外推边界。
> - 未嵌入原因：仅保存 Markdown / 许可限制 / 资产不可稳定迁移。
```

“未嵌图”不降低科学要求；它只改变呈现载体。Agent 必须实际打开并检查视觉输入，不能根据 caption 或 OCR 猜图。

### 7.4 默认 Markdown 写法

```markdown
![外部测试集上的性能变化：方法在中心 B 上优势明显缩小](./assets/<paper-key>/table-03-external-test.png)

*来源：原论文第 8 页，Table 3。读图重点：中心 A 上 Dice 提升 3.1 个百分点，但中心 B 仅提升 0.7，且未给出中心间差异的统计检验。*
```

需要控制宽度时，可使用 HTML：

```html
<figure>
  <img src="./assets/<paper-key>/fig-02-method-overview.png"
       width="900"
       alt="方法流程图：输入影像先经过共享编码器，再由边界分支和区域分支联合训练，推理时只保留区域分支">
  <figcaption><strong>原论文 Fig. 2：</strong>边界分支只在训练阶段存在，因此作者声称不会增加推理成本。</figcaption>
</figure>
```

### 7.5 复杂图必须有文字等价物

对曲线图、散点图、热图、流程图和多面板医学影像图，alt text 和正文解释至少说明：

- 图在比较什么；
- 横纵轴、单位和分组；
- 主要趋势或异常；
- 对核心结论最重要的数据点；
- 哪些内容无法从图中推出。

### 7.6 不允许出现的写法

```markdown
- Figure 4：支持本文结论。
- Table 2：效果很好。
- 详见原文图片。
```

这种写法既不可读，也无法审计。

## 8. A-core 深读必须覆盖的科学内容

### 8.1 一屏决策摘要

控制在读者一屏可看到的范围内，但必须有信息密度：

- 论文一句话：研究对象、方法和主要发现；
- 论文类型：理论、方法、系统、临床预测、诊断、综述等；
- 最重要的 1–3 个贡献；
- 最强证据；
- 最大局限；
- 当前可信度判断；
- 是否值得复现、采用、引用或继续追踪；
- 与项目的关系只写一句，详细内容放后面。

### 8.2 问题、背景与贡献拆解

必须回答：

1. 论文要解决的科学或工程问题是什么？
2. 现有方法为什么不够？瓶颈是数据、目标函数、表示、优化、评价，还是部署条件？
3. 作者把问题形式化成什么输入、输出、约束和目标？
4. 作者声称的贡献分别属于：
   - 新问题或新任务；
   - 新方法或新算法；
   - 新机制解释；
   - 新数据、基准或评价；
   - 新实证发现；
   - 新临床/系统验证。
5. 哪些贡献真正被实验证明，哪些只是设计描述或未来可能性？
6. 新颖性来自核心机制，还是多个已有部件的组合、扩大数据规模或更强训练预算？

贡献应写成完整的科学句子，并给出证据位置。

### 8.3 数据与研究设计审计

对实证论文，至少覆盖：

- 数据来源、时间范围、机构、公开/私有、前瞻/回顾；
- 纳入与排除标准；
- 样本、患者、图像、切片或事件的数量关系；
- 标签/参考标准如何产生，标注者数量、资历、协议和分歧处理；
- 缺失值、异常值、重复样本、数据清洗；
- 训练、调参、内部测试、外部测试的划分比例和划分单位；
- 是否存在同一患者、同一检查、同一来源或时间泄漏；
- 数据分布、类别不平衡、亚组代表性；
- 预处理、归一化、重采样、裁剪、数据增强；
- 数据是否匹配声称的目标人群和使用场景；
- 样本量或功效是否足以支撑主结论。

推荐配一张“样本流与数据划分”图或表。

### 8.4 方法或理论重建

不能只抄模型名称。至少说明：

- 输入、输出与任务定义；
- 核心表示或状态；
- 每个关键模块负责解决什么问题；
- 训练数据如何流动；
- 损失函数各项的含义、权重和作用；
- 优化器、学习率、批大小、训练轮次、停止条件；
- 推理阶段与训练阶段有什么不同；
- 后处理、阈值和模型选择规则；
- 算法复杂度、参数量、显存、延迟或数据需求；
- 方法成立依赖哪些假设；
- 这些假设被违反时会怎样失败。

理论论文额外说明：

- 定义、主要定理和假设；
- 证明的核心思路，而不是逐行誊写；
- 结论的适用域、紧致性和反例；
- 理论量与实际实验量之间如何对应。

### 8.5 关键结论—证据包

不要用一张大表取代推理。每个核心结论单独形成一个可阅读的证据包。

```markdown
### 关键结论一｜<用自然语言写清结论>
<!-- claim_key: optional-machine-key -->

**作者主张**
<作者声称什么。>

**证据位置**
<Section、页码、Figure/Table/Equation、supplement。>

![<能够表达图中关键信息的替代文字>](./assets/<paper-key>/<image>.png)

**关键数字与比较条件**
- 数据集与样本量：
- 基线与训练预算：
- 指标与数值：
- 方差、置信区间或统计检验：

**它实际支持什么**
<证据允许得出的最强结论。>

**它没有支持什么**
<外推、因果、泛化、临床影响等边界。>

**最强替代解释**
<更大模型、不同预处理、调参优势、数据泄漏、选择性报告等。>

**可信度判断**
高 / 中 / 低，并用两三句话解释，不只给标签。
```

A-core 默认应有 3–7 个这样的证据包，覆盖论文真正的主张，而不是按章节机械凑数。

### 8.6 数值结果与统计审计

每个主要结果至少检查：

- 比较双方是否使用相同数据、预处理、训练预算、调参力度和模型选择规则；
- 报告的是最好一次、均值、中位数，还是预注册主分析；
- 重复次数、随机种子和方差；
- 效应大小，而不只看是否“显著”；
- 标准差、标准误、置信区间或其他不确定性；
- 统计检验是否适合，独立性假设是否满足；
- 是否存在多重比较、重复挑选数据集或指标；
- 指标是否匹配真实目标，是否被类别不平衡掩盖；
- 性能差异是否有实际/临床意义；
- 缺失的数字会如何改变结论。

推荐结果表：

| 研究问题 | 比较条件 | 关键数值 | 不确定性 | 是否公平 | 能支持的结论 | 主要保留意见 |
|---|---|---:|---|---|---|---|

不要把 `Table 2` 作为首列；首列应是读者关心的研究问题。

### 8.7 图表解读与视觉证据册

每张关键图表必须回答：

1. 它在比较什么？
2. 哪个视觉元素承担主要证据？
3. 图中最重要的数字、趋势、异常或反例是什么？
4. 图的坐标、截断、归一化或聚合方式会不会误导？
5. 它支持正文哪条主张？
6. 它不能支持什么？
7. 是否存在正文强调、但图中并不稳健的结论？

### 8.8 消融、稳健性、分层与失败案例

深读不能只看主结果。必须检查适用的：

- 模块消融；
- 损失项与超参数敏感性；
- 数据规模、标签比例和噪声敏感性；
- 随机种子、初始化和训练稳定性；
- 域偏移、外部中心、时间漂移；
- 人群、设备、病灶大小、难例等亚组；
- 计算成本与性能权衡；
- 错误类型、典型失败图、混淆矩阵；
- 负结果和不奏效的设置。

若作者没有提供，必须把它列为“未被验证的关键边界”，不能沉默处理。

### 8.9 批判性评价：从“缺点列表”升级为有效性分析

至少从以下维度判断：

- **内部有效性：**观察到的差异真由方法造成吗？
- **构念有效性：**指标和实验设置真的测到了作者声称的能力吗？
- **统计结论有效性：**样本量、不确定性和分析选择能支撑结论吗？
- **外部有效性：**结论能迁移到哪些人群、机构、设备、任务和资源条件？
- **机制可信度：**消融或分析是否真正支持作者给出的机制解释？
- **选择性报告：**是否只展示有利指标、数据集、种子或案例？
- **部署差距：**离真实工作流还缺哪些环节？
- **利益冲突与独立性：**资金、数据拥有关系或商业依赖是否可能影响解释？

“作者承认的局限”和“阅读者识别但作者未充分讨论的局限”必须分开。

### 8.10 可复现性与可复用性

不要只写“有代码/无代码”。分别判断：

- 代码、数据、模型、配置、环境和分析脚本是否可获得；
- 是否有稳定归档地址或只是个人页面；
- 依赖版本、硬件和随机种子是否明确；
- 数据划分、预处理和模型选择规则是否可重建；
- 代码是否与论文主结果一致；
- 是否可以执行最小示例；
- 能否生成主表/主图；
- 是否只是“可访问”，还是已经被独立执行、复现或复制；
- 哪些缺失材料会阻断完全复现；
- 最小复现路径、预计资源和验收标准。

推荐结论分层：

- **材料可获得**：能访问相关代码/数据/模型；
- **材料可执行**：文档充分，最小流程能运行；
- **结果可复现**：不同人员用作者材料得到相容结果；
- **结果可独立复制**：不用作者材料也能得到相容结论。

### 8.11 文献位置与新颖性

至少选择 2–5 篇最接近的工作，回答：

- 谁最早提出相似问题或机制；
- 本文继承了什么；
- 真正改变了什么；
- 比较是否遗漏了更强或更公平的基线；
- 本文结果是否与领域已有结果一致；
- 是解决了一个普遍问题，还是只在特定设置中有效；
- 论文之后是否已有复现、反驳或扩展。

差异矩阵：

| 工作 | 核心问题 | 方法机制 | 数据/场景 | 评价强度 | 本文相对差异 | 差异是否被证据证明 |
|---|---|---|---|---|---|---|

单篇论文卡不能声称“已穷尽文献”或“全球首创”；只能说明当前检索范围内的证据。

### 8.12 项目迁移：必须显式写出推理链

推荐格式：

| 论文内在发现 | 当前项目对应物 | 迁移所需假设 | 本地验证 | 若失败意味着什么 |
|---|---|---|---|---|

项目关系分为：

- **直接支持**：任务、数据、机制和评价条件高度相近；
- **间接先例**：机制相似，但至少有一项关键条件不同；
- **仅启发**：只提供想法，不能当证据；
- **不能支持**：与当前论证存在冲突、条件不匹配或证据不足。

任何项目迁移句都必须能追溯到前文的论文内在证据，而不是凭相似词汇建立关联。

### 8.13 下一步必须是决策动作

不要只写“继续阅读”“进一步研究”。应明确：

- 可直接复用的模块、数据处理、指标或实验设计；
- 必须先验证的假设；
- 最小复现实验；
- 需要补读的具体论文或方法；
- 需要向作者/仓库核实的问题；
- 不允许写进当前论文的过度结论；
- 触发采用、放弃或转向的证据阈值。

## 9. 按论文类型加载扩展模块

通用模板不能覆盖所有研究设计。应按论文类型加载附加审计，而不是让所有论文都填同样的空字段。

### 9.1 经验机器学习/算法论文

额外检查：

- 调参预算与基线是否对等；
- 测试集是否被反复使用；
- 随机种子和方差；
- 计算量、参数量和数据量公平性；
- 消融是否能区分机制贡献和容量贡献；
- 多数据集、多任务和域偏移；
- 预训练数据是否可能污染测试集；
- 指标实现和评测脚本是否一致。

### 9.2 医学影像 AI 论文

额外检查：

- 预期临床用途：筛查、分诊、诊断、分割、预后、监测或工作流辅助；
- 回顾性/前瞻性、单中心/多中心；
- 患者、检查、序列、切片之间的层级关系；
- 患者级或更高层级的数据独立划分；
- 图像采集协议：设备、序列、层厚、分辨率、重建参数；
- 纳入排除、人口学和临床特征；
- 参考标准的定义、标注者资历、协议、分歧解决和一致性；
- 预处理、配准、重采样、窗宽窗位、裁剪与去标识；
- 缺失数据和不平衡处理；
- 内部测试与外部测试的明确区分；
- 置信区间、校准、灵敏度/特异度、病灶级与患者级指标；
- 亚组、最差表现人群和失败案例；
- oracle 信息、人工交互或未来信息是否进入可部署流程；
- 临床基线、人类读者或现有工作流比较；
- 真实部署中的时间、资源、监管和责任边界。

### 9.3 临床预测模型论文

额外检查：

- 目标人群、预测时点、预测窗口和结局定义；
- 候选预测变量如何选择；
- 缺失值处理；
- 过拟合控制；
- 区分开发、内部测试和外部测试；
- 区分判别、校准和临床效用；
- 模型是否提供完整系数、代码或可执行工具；
- 更新、再校准和域迁移条件。

### 9.4 随机对照试验

额外检查：

- 随机化过程与分配隐藏；
- 偏离既定干预；
- 缺失结局；
- 结局测量偏倚；
- 选择性报告；
- 意向治疗与符合方案分析；
- 不良事件与实际效应大小。

### 9.5 系统综述/Meta 分析

额外检查：

- 协议与预注册；
- 检索数据库、检索式和时间范围；
- 纳入排除标准；
- 筛选流程图；
- 偏倚风险评价；
- 效应量、异质性和模型选择；
- 发表偏倚和敏感性分析；
- 证据确定性；
- 结论是否超出纳入研究质量。

### 9.6 理论论文

额外检查：

- 主要定理的前提是否现实；
- 证明中的关键技巧和不可省略步骤；
- 上下界是否紧；
- 是否存在反例或退化情形；
- 与已有定理相比真正新增什么；
- 理论结论与实验现象是否一致。

## 10. 可用状态：用人能理解的判断，不用状态码代替解释

正文顶部推荐写：

- **可用于研究决策**：核心结论、证据、边界和复现条件已闭环。
- **可用但有重要限制**：主要发现可参考，但某些条件会显著影响迁移或可信度。
- **需要补证**：缺少一项会改变判断的关键材料，例如补充结果、数据划分或统计信息。
- **暂不可用**：来源不可靠、主结论与证据不一致、存在严重泄漏/比较失真，或无法判断核心结果。

任何状态后面必须跟 2–4 句解释。状态本身不是结论。

## 11. 硬性质量门槛

满足以下任一情况，A-core 不得标为“可用于研究决策”：

1. 主结论没有明确证据位置。
2. 论文存在关键图表，但 Markdown 只写图号，既没有可读截图，也没有完整文字等价物。
3. 经验论文没有说明数据划分单位和泄漏风险。
4. 主结果没有比较条件、样本量或不确定性说明。
5. 方法部分无法区分训练流程与推理流程。
6. 只列作者承认的局限，没有独立批判和替代解释。
7. 项目关系占据主体，论文本身分析明显不足。
8. 用不透明 ID、内部状态或英文短字段替代自然语言结论。
9. “有代码”被直接写成“可复现”，没有检查配置、数据、执行和主结果生成路径。
10. 图表、数值或引用存在疑似错误，但没有显式标出不确定性。

## 12. Agent 执行顺序：科学产出优先，不展示治理过程

### 第一步：建立来源与结构地图

- 确认论文版本、补充材料、代码和数据来源；
- 扫描目录、图、表、公式和附录；
- 找出可能承载主结论的 3–8 个视觉对象。

### 第二步：先做论文内在阅读

- 问题、贡献、数据、方法、主结果；
- 不读取当前项目提示，或暂不写项目关系，避免过早锚定。

### 第三步：检查并整理视觉证据

- 能稳定保存时使用语义化文件名并嵌入；不能保存时写完整文字等价物；
- 写来源、alt text、读图结论和关键数字；
- 必要时绘制“阅读者重建图”。

### 第四步：构建关键结论—证据包

- 每个主结论都绑定位置、截图、数字、边界、替代解释和可信度。

### 第五步：完成设计、统计、偏倚和复现审计

- 选择适用的论文类型模块；
- 缺失信息写成明确缺口，不得用猜测填空。

### 第六步：最后再写项目迁移和下一步

- 将每个迁移判断追溯到前文证据；
- 明确迁移假设与最小本地验证。

### 第七步：进行一次纯可读性重写

- 删除无意义 ID、重复字段和流程术语；
- 将表格中的重要结论提到正文；
- 有图片时检查是否清楚；无图片时检查文字等价物是否自足；
- 让非执行者可以顺畅读完。

Worker 数量、并行方式和内部 schema 均属于实现细节，不应成为主文档内容。

## 14. 最终验收问题

交付前，逐项回答“是/否”，但不要把该清单原样放进主文档：

1. 一个不认识内部 ID 的人能否顺畅读懂？
2. 前三条主结论是否都有真实证据位置、可读截图和关键数字？
3. 是否明确区分作者主张、直接证据、评审判断和项目迁移？
4. 是否能重建数据、训练、推理和评价流程？
5. 是否检查了比较公平性、不确定性、稳健性和失败案例？
6. 是否说明每张关键图“证明什么”和“不证明什么”？
7. 是否给出了最强替代解释，而不只是泛泛列局限？
8. 是否把代码可得性与结果可复现性分开？
9. 项目关系是否建立在论文内在证据之后？
10. 是否删除了对阅读无帮助的治理、版本和流程噪声？
